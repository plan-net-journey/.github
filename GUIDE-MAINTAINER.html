Verteilung

Wie Updates beim Team ankommen

Nichts passiert automatisch

Ein Merge auf main stellt die neue Version bereit — mehr nicht. Claude Code holt den Marketplace einmal beim Hinzufügen und danach nie wieder von selbst. Bis jemand /plugin marketplace update ausführt, arbeitet das Team mit dem Stand von damals.

Wenn du also einen Skill ausrollst: sag dem Team Bescheid, dass es aktualisieren muss. Sonst merkt es niemand.

Version bumpen ist Pflicht

Ohne Bump in plugin.json und marketplace.json sieht Claude Code keinen Grund, die neue Fassung zu ziehen.

Quelle prüfen wenn etwas nicht ankommt

Der Marketplace muss von GitHub kommen, nicht aus einem lokalen Ordner. Prüfen mit /plugin marketplace list — dort muss GitHub (plan-net-journey/Journey-Skills) stehen. Zeigt die Quelle auf einen Pfad, bekommt derjenige nie Updates.

Häufigste Ursache wenn jemand meldet „bei mir gibt es den Skill nicht“: alter Marketplace-Stand oder Claude Code seit dem Update nicht neu gestartet.

Teams-Benachrichtigungen

Einmal einrichten, Schritt für Schritt

Ohne das bekommt niemand mit, wenn ein Ticket aufschlägt oder eine Änderung auf Freigabe wartet. Dauert fünf Minuten. Jede Maintainer-Gruppe macht das für ihre Repos selbst — auch in Kunden-Repos.

1

Die richtige App installieren

In Teams links auf Apps, nach GitHub suchen. Es erscheinen drei. Du brauchst GitHub Notifications von Microsoft Corporation.

Nicht die App namens „GitHub“ (das ist eine Vorschau-Version für Code-Erzeugung) und nicht „GHEC“ (für Enterprise-Konten, habt ihr nicht).

2

Anmelden

Im Chat mit dem Bot eingeben:

@GitHub Notifications signin

Öffnet einen Browser-Login. Einmalig. Danach erscheinen deine Antworten auf GitHub unter deinem Namen — wichtig, damit Freigaben zugeordnet werden können.

3

Abonnieren

Im persönlichen Chat mit dem Bot — dort brauchst du kein @ davor:

subscribe plan-net-journey/admin-ops issues

subscribe plan-net-journey/Journey-Skills pulls, comments, reviews

Reihenfolge beachten: Repo zuerst, Ereignisarten dahinter. Komma nur zwischen den Ereignisarten, nicht nach dem Repo.

4

Kontrollieren

subscribe list features

Zeigt, was dieser Chat abonniert hat. Steht dort nichts, hat Schritt 3 nicht funktioniert.

Welche Ereignisarten es gibt

issues · pulls · comments · commits · reviews · releases · deployments · branches · discussions · workflows

Damit lässt sich die Sprache pro Person steuern. Wer keine Entwickler-Meldungen braucht, abonniert nur comments und bekommt dann ausschließlich die Klartext-Erklärungen, die unsere Workflows schreiben — nicht die technischen PR-Karten.

Antworten

Jede Karte hat unten einen Comment-Knopf. Der öffnet ein Textfeld; was du dort schreibst, landet als Kommentar auf GitHub.

Das ist der Weg, auf dem Freigaben zurückkommen.

Für Kunden-Repos genauso

Das Abo hängt an dem Ort, an dem du den Befehl tippst — nicht an einer Konfiguration im Code. Für einen Kunden also im Kanal dieses Kunden:

@GitHub Notifications subscribe plan-net-journey/<kunden-repo> pulls, comments

Kommt ein neuer Kunde dazu, tippt seine Maintainer-Gruppe einen Befehl in ihren Kanal. Kein Workflow anfassen, kein Secret, nichts deployen.
